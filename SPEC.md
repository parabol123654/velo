# Velo spec

What Velo is and the rules it keeps. This describes the current system, not a plan; open work lives in [GitHub Issues](https://github.com/parabol123654/velo/issues) (the order to take it in is under [Next](#next)), and defects in the current system are listed under [Known gaps](#known-gaps). Contributor rules are in [AGENTS.md](./AGENTS.md).

## Goal

A self-hosted issue tracker for individuals and small dev teams (1–25 people) and their coding agents. It covers the part of Jira small teams actually use, and nothing else.

Non-goals: enterprise permission matrices, custom fields, workflow engines, mail servers, plugins, multi-tenant hosting.

## Invariants

These hold for every change. Breaking one needs an explicit decision, recorded here.

1. **One binary, one data directory.** The web UI is embedded with `embed.FS`. Data is `<data>/velo.db` (SQLite, WAL, FTS5) plus `<data>/uploads/`. No CGO (`modernc.org/sqlite`), no required external service.
2. **Plain SQL.** Queries live in `internal/db/` on `database/sql`. No ORM.
3. **One write path.** The web UI, the CLI and the MCP server all change data through the HTTP API, so validation is shared and every mutation reaches open browsers over SSE. The CLI and MCP never open the SQLite file. Three exceptions, all server-side or offline: `velo backup` opens the file to run `VACUUM INTO` (and, like any open, runs `migrate()`); `velo uploads prune` opens it to delete unused uploads (decision for #4: it is maintenance on the data directory, and API tokens never reach admin actions); and the GitHub webhook writes through `internal/db` inside the server process and broadcasts itself.
4. **Schema changes are additive and automatic.** `migrate()` runs the `CREATE ... IF NOT EXISTS` schema, then adds columns that older databases lack (`addColumn`) and rebuilds derived data whose definition changed (the search index). A v0.1 database must open in any later version.
5. **Every change ships with a check:** `go test ./...`, `npm test` and `npm run build` in `web/`.

## Domain

| Concept | Rules |
| :-- | :-- |
| Project | Unique `key` of 2–10 uppercase letters or digits, starting with a letter (`DEV`). Issue numbers come from `issue_seq`, incremented in the same transaction as the insert, so keys never collide. |
| Workflow state | Per project, any name, but each belongs to one category: `backlog`, `unstarted`, `started`, `completed`, `canceled`. New projects get Backlog, Todo, In Progress, In Review, Done, Canceled. |
| Issue | `KEY-N` identifier, optional parent in the same project (sub-issues; deleting a parent detaches its children; a parent change that would make a loop is refused with 400), Markdown description, priority 0–4 (none, low, medium, high, urgent), optional assignee and cycle, labels by ID or name (a label the project does not have is refused with 400 naming it, and nothing is written). A `PATCH` sends only the fields to change; there is no version check, so the last write wins. |
| Issue link | Between two issues of the same project: `blocks`, `relates` (symmetric) or `duplicates`. The API also takes `blocked_by` and `duplicated_by` and stores the reversed form. A `blocks` link that would close a loop of any length is refused with 409 naming the existing chain. An issue's `blocked_by_count` counts blockers not yet completed or canceled; finishing, reopening or deleting a blocker pushes `issue.updated` for the issues it blocks. Unlinking removes every link between the pair. |
| Picking up work | `next` returns the issue to start: state category `unstarted`, unassigned, not blocked; highest priority first with "no priority" last, then board order. Optional project and label filters. `claim` assigns it to the caller and moves it to the project's first `started` state; it fails with 409 if someone else holds it, it is finished, or it is blocked. The check and the write run in one transaction with a conditional `UPDATE`, so of a claim and a concurrent claim or manual assignment exactly one takes effect; updates always read the current row inside their transaction. |
| Checklist | `- [ ]` / `- [x]` lines in a description, outside code blocks. Clients can set one item by 1-based index or by text (exact match first, else a unique substring); setting is idempotent and logs a short `checklist` activity. |
| Ordering | `position REAL`. A drop between two cards takes the midpoint, so a move updates one row. |
| Cycle | Optional sprint with dates and status `upcoming`, `active`, `completed`. A `PATCH` sends only the fields to change, like issues; an empty string clears the description or a date, and the name cannot be empty. |
| Comment, activity, attachment | Comments are Markdown; the author or an admin may edit or delete one. Activities record creation; changes to title, state, priority, assignee, cycle, `labels` (old and new names), `parent` (old and new identifier) and `description` (that it changed, not the text); links and unlinks (`link`, on both issues, each from its own side with the kind: `blocks DEV-2` / `blocked_by DEV-1`); and checklist ticks (`checklist`). A patch that changes nothing logs nothing. Uploads (max 20 MB) go to `uploads/`. An upload belongs to the issue it was made for, or, if made before the issue existed, to the first issue or comment its uploader saves with a link to it (nobody else's link claims it); access then follows that issue's project. An upload no issue owns is served only to its uploader and admins, never through a project-restricted token (so such a token cannot read back an upload it made without `issue_id`). Deleting an issue deletes its uploads and their files, except uploads another surviving issue or comment of the same project still links, which move to that issue; deleting a project deletes all of its uploads. `velo uploads prune` (a dry run unless `--apply`) removes what older versions left behind: files in `uploads/` with no attachment row, and uploads no issue owns that no description or comment links; both only when older than 24 hours, so an upload in progress or pasted into an unsaved form is kept. Uploads are served only to signed-in users; PNG, JPEG, GIF and WebP display inline, anything else downloads. |
| Search | FTS5 over identifier, title and description, kept in sync by triggers. Accents fold, so `dang nhap` finds `đăng nhập`: the tokenizer is `unicode61 remove_diacritics 2` (strips every mark, including two on one letter, as in `ậ`), and `đ`/`Đ`, a separate letter rather than an accented `d`, become `d` in the indexed text (the `issues_fts_src` view) and in the query. Decision (gap 8): the index is derived data, so `migrate()` drops and rebuilds it once when it predates this; issues are untouched and Invariant 4 holds. Each word is a prefix match, all words must match. Comments are not indexed. |
| Query syntax | One string for filters and search, parsed server-side (`ParseIssueQuery`) into the issue filter: `assignee:me|none|<email>`, `state:<name>`, `label:<name>` (repeatable: all must match), `priority:<0-4 or none, low, medium, high, urgent>` with optional `=`, `>`, `>=`, `<`, `<=`, `cycle:<name>|none`, `project:<KEY>`, `parent:<KEY-N>`, `is:open|closed|blocked|unblocked` (open: not completed or canceled), `has:parent`, `no:parent`. Keys are case-insensitive; values with spaces, and free text containing a colon, go in double quotes; the remaining words are full-text search. An unknown key, a missing value, a repeated key (except `label`), contradictory `is:` values or an unclosed quote is a 400 naming the problem. Keys are ASCII letters, so `10:30`, `lỗi:` and URLs stay text. A query longer than 1000 bytes or 50 words is a 400, which keeps it inside SQLite's limits. A value that names nothing (`label:nosuch`, `state:Nosuch`) matches no issue rather than erroring, as the separate parameters do. Used by `q` on `GET /api/issues` (combined with the separate parameters; setting the same field both ways is a 400) and `GET /api/search`, MCP `list_issues`/`search_issues` `query`, and the CLI `--q` and `velo search`. |
| Saved filter | A named query of one user (`saved_filters`: name of 1–80 characters, unique per user ignoring case (Unicode, so `Lỗi` and `LỖI` clash), query that must parse, position). `GET/POST /api/filters`, `PATCH/DELETE /api/filters/{id}`; another user's filter is 404. Filters have no project: any token of the user may use them (a read-only token only lists). Not exported (export is per project), not broadcast (only their owner sees them), deleted with their user. The web UI applies a query on the board and lists (it asks `/api/issues?project=KEY&q=` which issues match, again after each change), shows syntax errors, saves the query, and lists saved filters in the sidebar. |
| Export/import | Per project, Markdown (read-only) or JSON (round-trips through import, issue links included). Import checks labels, workflow states and links against the bundle before it creates anything. A bundle state named like a default state sets that state's category, color and position; the others are created; defaults the bundle lacks stay. Label and state names match ignoring case, Unicode included (`LỖI` finds `lỗi`). |
| Import from other trackers | `POST /api/projects/{ref}/import` takes a batch (`db.ImportBatch`: a `source` name, issues by `external_id` with title, Markdown description, state by name or `state_category`, priority, label and cycle names, assignee email, parent and comments by external ID, original `created_at`, plus links) and imports it into an existing project. The batch runs in one transaction: any problem (unknown state, a parent or link end that is neither in the batch nor imported earlier from the same source, a blocking loop, a `blocks` or `duplicates` link that exists the other way round, a parent loop, a repeated external ID, an issue ID starting with `comment:`) is a 400 naming it and nothing is written; `?dry_run=1` (or `true`; `0`, `false` or none for a real import, any other value is a 400) does the same work and rolls it back, returning the same report. One request takes at most 5000 issues, 20000 comments, 10000 links and 32 MB. Issues get new `KEY-N` numbers in batch order and keep their original `created_at`; the description ends with a quote line naming the original (`> Imported from [owner/repo#12](url), opened by @a`), with names from the other tracker made plain (brackets become parentheses) and a code fence the source left open closed. When no enabled user has the assignee's email (or the assignee is `me`), the issue stays unassigned and the footer and the report name the assignee. Missing labels and cycles are created (names match ignoring case, Unicode included). Comments are posted by the importer; when the source names their author, a first line gives it and the date as written there (`**@bob** · 2024-03-02`). `import_refs` records which external issue or comment became which row, per project and source, so a rerun skips issues already imported (leaving edits made in Velo) and adds only comments, parents of new issues and links it has not made yet; deleting an imported issue or comment drops its record. `import_refs` is not exported: after a project export and import, a rerun from the original source imports everything again. Loop checks walk the project's `blocks` links in memory, so a big batch does not hold the database for long. A real import sends one `project.updated`. |

## Accounts and access

- **First run:** the first visitor creates the admin. After that, accounts come from single-use invite links (7 days) or are created by an admin. No email is sent.
- **Roles:** `admin` and `member`. Members can do everything with projects and issues. Only admins manage users and invites.
- **Credentials:** browser sessions are `HttpOnly`, `SameSite=Lax` cookies valid 30 days, `Secure` when the request came over HTTPS (TLS, or `X-Forwarded-Proto: https` with `--trust-proxy`) (`vs_` tokens, also accepted as Bearer). API tokens (`velo_` prefix) are for the CLI and MCP. Only SHA-256 hashes are stored; passwords use bcrypt, minimum 6 characters.
- **Password change:** a user changes their own password with the current one. Their other sessions are signed out; the current one stays.
- **Admin actions:** reset a user's password (signs out all their sessions), change role, disable or enable, delete.
- **Disable:** login, sessions and API tokens stop working at once, and sessions are deleted. Tokens come back if the user is enabled again. History stays intact.
- **Delete:** only for users with no history (created issues, comments, activity, uploads). Otherwise the API answers 409 and the admin disables instead.
- **Guards:** an admin cannot change or delete their own account through these endpoints, and the last enabled admin cannot be demoted, disabled or deleted.
- **Login throttling:** after 5 failed logins within 15 minutes from one client IP or for one email, further attempts (even correct ones) get 429 with `Retry-After` until 15 minutes after the first failure. A successful login clears the email's counter. Counters live in memory. The IP is the TCP peer, or with `--trust-proxy` the last address in `X-Forwarded-For`.
- **Reverse proxy (`velo serve --trust-proxy`, or `VELO_TRUST_PROXY=1` or `true`):** off by default, because any client can send forwarding headers. Decision (gap 10): with it, `X-Forwarded-Proto: https` makes the session cookie `Secure`, and login throttling keys on the last `X-Forwarded-For` address, the one the proxy appended; earlier addresses come from the client and are ignored. For both headers the last header line counts; an address may carry a port, brackets or an IPv6 zone, and one that does not parse falls back to the TCP peer. This assumes exactly one proxy in front of Velo; behind a chain (CDN, then nginx) the counted IP is the inner proxy's.

### API token scopes

A token acts as its user, narrowed by its scope (set at creation, shown in Settings):

- **Access:** `write` (default) or `read`. A read token may only use `GET`.
- **Projects:** empty means every project. Otherwise the token only sees and changes those projects: lists, search and the SSE stream are filtered; requests for objects elsewhere get 403; creating or importing projects is refused. Deleting a listed project does not widen the token.
- **Never with a token:** managing tokens, changing the password, and every admin endpoint, even for an admin's token.
- Every authenticated route declares its token rule in `routes()` (`internal/server/scope.go`), so a new route cannot skip the check.
- Attachments not yet linked to an issue are served to any signed-in caller; their random URL is the capability.

### Attribution

Comments and activities made through an API token record the token's name (`via`), shown as "via Claude Code" in the UI and CLI and included in the JSON and SSE payloads. Browser sessions record nothing, so people and agents can be told apart.

## Live updates

`GET /api/events` is a Server-Sent Events stream. Each message is `{"type": ..., "payload": ...}`:

| Event | Payload | Web UI handling |
| :-- | :-- | :-- |
| `issue.created`, `issue.updated` | full issue | Upsert that card; refetch affected parent cards; debounced refetch of project and cycle counters |
| `issue.deleted` | `{id, identifier}` | Remove the card, detach its sub-issues |
| `comment.created`, `comment.deleted` | comment, or `{id, issue_id}` | Adjust the card's comment count |
| `comment.updated` | comment | Nothing on the board; an open drawer refreshes |
| `project.*`, `state.updated`, `cycle.*`, `label.created`, `user.created`, `user.updated`, `user.deleted` | object | Debounced full workspace reload |
| `label.deleted` | `{id}` | Debounced full workspace reload |

Linking, unlinking, claiming and checklist ticks send `issue.updated` for every issue whose data changed. New users are broadcast whether an admin created them or they accepted an invite.

Each event belongs to a project (user events to none); a project-restricted token's stream only gets its projects' events. The board logic is the pure function `applyEvent` in `web/src/live.ts`. A slow client may miss events (the hub drops them when its buffer is full); the UI reloads once whenever the stream reconnects.

## Integrations

- **CLI:** `velo serve | login | project | issue | label | cycle | user | search | mcp | backup | uploads | agent | import | version`. `velo issue` covers `list | show | create | update | delete | comment | next | claim | check | link | unlink`. `velo cycle` covers `create | update` (a cycle by name or ID; only the flags given change). `velo import file BATCH.json --project KEY [--dry-run]` sends an import batch from a file. A batch over one request's limits is sent in several, parents before children and links last; a dry run then checks each request alone and says so, since parents and links between requests only resolve in the real run; source-specific importers read the other tracker on the client and send the same batch, so the CLI still never opens the database. `velo import github OWNER/REPO` reads issues (pull requests are skipped), all comments, milestones (as cycles: closed → completed, open → upcoming, due date → end date) and sub-issues of the same repository through the GitHub REST API, following `Link` pages only on the API host; an open issue goes to the first `unstarted` state, a closed one to `completed`, or `canceled` when closed as not planned or duplicate; the first assignee maps to a Velo user by `--map-user LOGIN=EMAIL`, otherwise the footer names `@login`. External IDs use the lower-cased `owner/repo`, so typing the name in another case does not import again. The GitHub token is only sent to the API host: next-page links and redirects to another scheme or host are refused, and `GITHUB_TOKEN` / `GH_TOKEN` are used only for `api.github.com`; another `--github-api` host (GitHub Enterprise) needs `--github-token`. GitHub has no priorities, so issues import with none. `velo import jira EXPORT.csv` reads Jira's "Export CSV (all fields)": repeated `Labels`, `Sprint` (the last one becomes the cycle, with no dates and status upcoming) and `Comment` (`DATE;AUTHOR;BODY`) columns; rows of empty cells are skipped, and a file separated by semicolons is refused with a message saying so. The state is a `--state-map STATUS=STATE` entry, taken as given (a state the project lacks is an error), else a done issue with a resolution such as Won't Do or Duplicate goes to the first canceled state whatever its status is called, else the status name when the project has that state, else the `Status Category` (To Do → unstarted, In Progress → started, Done → completed), or a guess from the status name when that column is missing. Priorities Highest/High/Medium/Low/Lowest become 4/3/2/1/1; other names import as none, with a warning naming them. Sub-tasks find their parent by issue ID or key; `Outward/Inward issue link (Blocks|Duplicate|Relates)` become links. Parents and links that point outside the file are left out with a warning, so an import split over several files (Jira exports at most 1000 issues per file) loses those between files. Two issues that block each other make the import a 400; remove one of the links from the file. Jira writes dates in the exporting user's format and time zone without saying which: they are read as UTC, and a column whose dates cannot be read is named in a warning and those issues and comments get the import time. Issue types, components, versions, worklogs and attachments are not imported; the description keeps Jira's wiki markup. Comments have no IDs in the CSV, so a comment is known by its place on the issue (`WEB-1#c2`). `VELO_URL` and `VELO_TOKEN` override the saved config (`~/.config/velo/config.json`).
- **MCP (stdio):** hand-written JSON-RPC in `internal/mcp` (no SDK), protocol version `2024-11-05`, results as text. It calls the HTTP API through `internal/client`, so it needs a running server and a token. Tools `list_projects`, `get_project`, `list_users`, `list_issues`, `get_issue`, `create_issue`, `update_issue`, `delete_issue`, `next_issue`, `claim_issue`, `check_item`, `link_issues`, `unlink_issues`, `add_comment`, `search_issues`, `create_label`, `create_cycle`, `update_cycle`, `export_project`.
- **MCP resources:** `velo://project/<KEY>` (listed) and `velo://issue/<KEY-N>` (template), as Markdown: an issue includes its links, sub-issues and comments.
- **MCP prompts:** `work_on_issue` (claim → work → `check_item` → comment → review), `split_issue` (propose, then create sub-issues and `blocks` links), `summarize_cycle`. Each embeds the current issue or cycle so the agent starts with context.
- **Agent runner (`velo agent`):** a client-side loop, never run by the server. It wakes on SSE events (and every `--poll`), takes `next` for its label/project, `claim`s it, runs `--cmd` with the `work_on_issue` prompt, and comments the result (exit code, duration, last ~3 KB of output). The command is split into arguments and executed without a shell; the prompt is passed as one argument (`{prompt}`) or on stdin. One run at a time; a failed, timed-out or interrupted run leaves the issue assigned to the agent, so it is never retried automatically. A failed claim waits for the next event instead of retrying.
- **Version:** one value, `internal/version.Version`, set at build time with `-ldflags -X` by the Makefile (`git describe`), the Dockerfile (`--build-arg VERSION=...`) and the release workflow (the tag). `velo version`, the `velo serve` banner and MCP `serverInfo.version` all print it; a plain `go build` reports `dev`.
- **Friendly references:** wherever the API takes an assignee it also accepts an email or `me`; cycles accept a name; parent filters accept an identifier. Disabled users cannot be assigned.
- **GitHub webhook:** `POST /api/webhooks/github`, enabled by `--github-secret` or `VELO_GITHUB_WEBHOOK_SECRET`. Commits and PRs that mention `KEY-N` get a comment. `Fixes`, `Closes` or `Resolves KEY-N` on the default branch (or a PR merged into it) moves the issue to the first completed state. Comments are posted as the user with the matching email, otherwise as a built-in "GitHub" user that cannot log in.

## Known gaps

Places where the code falls short of this spec or of the rules in [CONTRIBUTING.md](./CONTRIBUTING.md). Each is small; fix it test-first (the "Done when" line is the test), then delete the entry in the same PR. Last reviewed at commit `ceaf004` on 2026-11-26; gaps 1–11 found then are fixed.

1. **JSON import drops cycles it cannot create.** `ImportProjectJSON` ignores `CreateCycle` errors, and an issue whose cycle the bundle does not define is imported with no cycle, silently. Done when: an import whose issues name an unknown cycle, or whose bundle cycle is invalid (empty name, bad status), is a 400 naming it and creates nothing.
2. **JSON import keeps defaults the source project no longer has.** A source that renamed "Done" to "Shipped" or deleted "In Review" gets both back next to its own states after export and import. Done when: importing a bundle whose states omit a default leaves the new project with exactly the bundle's states (an unused default is removed), and an issue in a removed default is refused before anything is created.
